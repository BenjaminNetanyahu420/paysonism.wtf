# Payson Mercury Portfolio + Forum

A plain HTML/CSS/JavaScript portfolio with a persistent public chat and a D1-backed Mercury community forum.

## Requirements

- Node.js 20 or newer
- npm (included with Node)

No shell-specific tooling is required. The project scripts work in PowerShell, Command Prompt, macOS Terminal, and Linux shells.

## Start working locally

```text
npm install
npm run dev
```

Open `http://127.0.0.1:8787`, then visit `forum.html`. To use a different port, run `npm run dev -- --port=3000`.

`npm run dev` now runs the actual Worker and local D1 database through Wrangler, so the forum API behaves like production. Apply the D1 migrations locally after adding or changing them with `npx wrangler d1 migrations apply DB --local`.

## Commands

| Command | Purpose |
| --- | --- |
| `npm run dev` | Start the local site and local chat API. |
| `npm run test` | Run the chat behavior tests. |
| `npm run build` | Create deployable output in `dist/`. |
| `npm run verify` | Test, build, and verify required deployment files. |
| `npm run clean` | Remove generated `dist/` output. |
| `npm run db:generate` | Generate a new production database migration after editing `db/schema.ts`. |

## Project map

- `index.html` — portfolio content and site structure.
- `forum.html` — Mercury-themed community forum page.
- `css/mercury.css` — all visual styling.
- `theme/` and `assets/` — images and existing Y2K UI assets.
- `js/chat.js` and `js/forum.js` — browser clients.
- `worker/index.js` — production Worker with chat and forum APIs.
- `db/schema.ts` and `drizzle/` — production database schema and migrations.
- `scripts/` — cross-platform developer scripts.

## Production forum configuration

Production uses a Cloudflare Worker with a D1 database binding named `DB`. Apply every migration in `drizzle/` before deploying the Worker.

Configure these values outside the repository:

| Value | Purpose |
| --- | --- |
| `FORUM_OWNER_HANDLES` | Comma-separated owner handles, for example `payson,admin`. |
| `TURNSTILE_SITE_KEY` | Public Cloudflare Turnstile site key. |
| `TURNSTILE_SECRET` | Server-only Turnstile secret. |
| `CATBOX_USERHASH` | Server-only Catbox account token used by the upload relay. |

Set `FORUM_OWNER_HANDLES` and `TURNSTILE_SITE_KEY` as Worker variables, and set `TURNSTILE_SECRET` and `CATBOX_USERHASH` with `wrangler secret put`. The site key and secret must be generated by the same Turnstile widget, whose hostname allow-list must include the deployed site hostname. The Worker suppresses account forms until it has both values, and every sign-in or registration token is posted server-side to Cloudflare Siteverify.

From the Cloudflare account and Worker that actually serves the site, install the secret without committing or echoing it:

```bash
npx wrangler secret put TURNSTILE_SECRET
```

Confirm the binding name only (not its value) with `npx wrangler secret list`, then deploy the Worker. For local account testing, copy `.dev.vars.example` to `.dev.vars`; its explicit flag enables Cloudflare's documented Turnstile test keys. Uploads remain disabled until `CATBOX_USERHASH` is configured.

Forum posts are Markdown rendered with vendored `marked` and sanitized with `DOMPurify`. Raw HTML is removed. Forum files are forwarded to Catbox and only the returned public URL plus attachment metadata are stored in D1. Owners can hide forum content immediately; manage the corresponding external file through the site-owned Catbox account.

For normal visual work, use `npm run dev`. The local server is intentionally separate from the production Worker so you can change HTML, CSS, client JavaScript, and assets without cloud credentials. Before deploying production changes, run `npm run verify`.
